## Correction (2026-09-03) — the Go SDK claim below was wrong

The original Part 2 and Part 6 below state AssemblyAI has an "official SDK" for Go and treat that as a concrete point in Go's favor over Rust. **That was checked by existence only ("the repo is there"), not by maintenance status, and it was wrong.**

Verified directly against the GitHub API and each repo's own README (2026-09-03):

| SDK | Status | Evidence |
|---|---|---|
| Go | **Archived, discontinued April 2025** | `archived: true`, `pushed_at: 2025-04-01`. README: "As of April 2025, AssemblyAI Go SDK has been discontinued and will no longer be maintained." |
| Java | **Archived, discontinued April 2025** | Same archive date, same README notice, word-for-word. |
| Ruby | **Archived, discontinued April 2025** | Same. |
| C# | **Archived, discontinued April 2025** | Same. |
| Python | **Actively maintained** | Commits and a released version (1.3.0) same day as this correction; ongoing PR activity. |
| Node/JavaScript | **Actively maintained** | Commits and a released version (4.37.1) within the last two days; ongoing feature work. |

So the prior report didn't just miss one discontinued SDK — it cited four repos (Go, Java, Ruby, C#) as evidence of "official SDKs" when all four were archived by AssemblyAI in the same April 2025 sweep. Only Python and Node/JavaScript are actually maintained. The mistake was structural: "a GitHub repo exists at that URL" was treated as "AssemblyAI actively maintains this," without opening the README or checking `archived`/`pushed_at`.

**What this changes for the recommendation:** Go's one concrete, factual edge over Rust — "Go has an official SDK, Rust doesn't" — is false. Neither Go nor Rust has an official, maintained AssemblyAI SDK. Both would talk to AssemblyAI's REST endpoints (Guardrails, LLM Gateway, session retrieval) with a plain HTTP client and hand-written request/response types: `reqwest`+`serde` for Rust, `net/http`+struct tags or `resty` for Go. This is a wash, not a Go advantage.

Everything else in Part 3-5 below - the AI-agent friction argument against Rust (borrow-checker/lifetime debugging, ORM error legibility, no comparable friction documented for Go) - was sourced independently of the SDK claim and still holds on its own. Re-examined here rather than assumed: those sources (Fortytwo Network tech report, dev.to field guide, rustify.rs) describe general Rust-with-AI-agent friction, not anything AssemblyAI-specific, so removing the SDK claim doesn't touch them.

**Corrected recommendation: still Go, not Rust, not Python - but for a narrower reason than before.** With the SDK asymmetry gone, the case for Go over Rust rests entirely on the AI-agent-friction evidence in Part 3: no borrow checker, no lifetimes, no documented pattern of agents fighting Go's idioms the way they fight Rust's, and Go's own error-handling style (explicit returns, no exceptions) produces less opaque failure modes for an agent to interpret than Rust's generic-heavy compile errors. That argument doesn't need an SDK to stand - it was never actually about AssemblyAI integration, it's about how much of the 30 days gets spent on language-fighting versus product logic. Removing the false SDK point makes the case for Go weaker in raw count of arguments (one fewer data point) but not different in conclusion, because the SDK point was never the load-bearing one - re-reading Part 6's own reasoning, the deciding sentence is the AI-agent-friction paragraph, with the SDK line as a secondary confirming detail, not the crux. Python remains excluded for the reason stated in the original Part 6: it's the safe, low-novelty default, correctly ruled out because captain explicitly asked for something outside his comfort zone, not because Python is technically inferior - if anything, this correction shows Python's own SDK claim was the one actually accurate one in Part 2, so Python's technical case is, if anything, slightly stronger than the original report gave it credit for, and it remains the fallback if the AI-agent-friction risk for Rust turns out to matter less in practice than the cited sources suggest.

## 1. What ComplyLine's backend actually does

Re-reading its entry in `docs/hackathon-ideas.md` (Tier 1, #1, R3-21): it "ingests **one** AssemblyAI Voice Agent API session and produces a scoped compliance report" — a consent-event check, an AI-disclosure-timing check, and a PII-pattern scan, using "AssemblyAI's Guardrails PII-redaction product" and "the LLM Gateway" directly, plus a pluggable regex/rule layer for industry-specific PII packs.

This confirms the framing in the captain's instruction: ComplyLine analyzes a **completed** session log after the fact. AssemblyAI's Voice Agent API itself is real-time and WebSocket-based (`wss://agents.assemblyai.com/v1/ws`, confirmed in this repo's own AssemblyAI capability summary), but ComplyLine's own job is downstream of that — it's a consumer of session artifacts (transcript, PII-redaction results, LLM Gateway calls), not a live voice-agent host. Every one of those consumer-side products (Guardrails, LLM Gateway, session log retrieval) is a plain REST/HTTP JSON API, not the streaming WebSocket protocol. **The backend does not need to speak AssemblyAI's real-time WebSocket protocol for its core loop.** This one fact removes the single biggest Rust-integration risk (hand-rolling a WebSocket+JSON streaming client) from the equation entirely — the actual job is: make HTTP calls, get JSON back, write rows to Postgres, serve JSON to a React frontend. This is API-orchestration work in the most literal sense, and none of the three languages is disqualified by the technical shape of the task.

## 2. Does AssemblyAI have an official Rust SDK?

No. Checked AssemblyAI's GitHub org directly: repos exist for [Python](https://github.com/AssemblyAI/assemblyai-python-sdk), [JavaScript/Node](https://github.com/AssemblyAI/assemblyai-node-sdk), [Go](https://github.com/AssemblyAI/assemblyai-go-sdk), [Java](https://github.com/AssemblyAI/assemblyai-java-sdk), [Ruby](https://github.com/AssemblyAI/assemblyai-ruby-sdk), and C#/.NET. **No Rust SDK, official or otherwise, found on crates.io.** A Rust backend calling AssemblyAI's HTTP endpoints (Guardrails, LLM Gateway, session retrieval) would use a generic HTTP client (`reqwest`) and hand-write the request/response structs — not exotic, but zero SDK convenience, no typed request builders, no maintained wrapper to lean on if AssemblyAI changes a field.

> **[CORRECTED 2026-09-03, see top of document]** The line originally here claimed "Go has an official SDK; Python has the most mature and heavily-used one," treating Go's SDK as an existing, maintained convenience alongside Python's. That was wrong: the Go SDK (along with Java, Ruby, and C#) was archived and discontinued by AssemblyAI in April 2025 and has had zero commits since. Only Python and Node/JavaScript are actively maintained. Go therefore has **no** SDK advantage over Rust — both languages would hand-write typed HTTP/JSON calls against AssemblyAI's REST API. Python's SDK claim was accurate and remains so (100K+ monthly downloads, actively released as of this correction).

## 3. Rust web framework maturity and AI-agent proficiency

Realistic Rust choices are **Axum** (Tokio-based, composable, the closest thing to a "modern standard"), **Actix-web** (actor-model, historically fastest in benchmarks, ~10-15% more req/s than Axum under load), and **Rocket** (macro-heavy DSL, best raw ergonomics, worse throughput). None of this matters much for ComplyLine specifically — an API-orchestration app calling a few external HTTP endpoints per request is nowhere near request-rate-limited by framework choice; all three would be overkill-fast for a 25-person hackathon demo. Axum is the more idiomatic pick given active Tokio-ecosystem alignment ([reintech.io 2026 comparison](https://reintech.io/blog/axum-vs-actix-web-vs-rocket-rust-framework-comparison-2026)).

The real question is whether an AI coding agent can drive Rust development fast enough for a 30-day build. Evidence is mixed but converges on "usable, with real friction, better than a year ago, still behind Python/Go":

- Rust remains the hardest mainstream target for code-generation models: "general-purpose code generation models trained primarily on high-level, garbage-collected languages such as Python, JavaScript, and Java often fail to internalize Rust's unique idioms" ([Fortytwo Network / Strand-Rust-Coder tech report](https://huggingface.co/blog/Fortytwo-Network/strand-rust-coder-tech-report)).
- Model-specific proficiency has genuinely improved and is now assistant-dependent: "GPT-5.5 currently has the cleanest Rust borrow-checker reasoning of any agent. Claude Code is close behind; Cursor lags slightly on Rust specifically" ([dev.to field guide, 2026](https://dev.to/thedailyagent/python-vs-go-vs-rust-for-ai-agents-in-2026-a-pragmatic-field-guide-5fda)).
- Agents are explicitly called out as **unreliable for up-to-date crate versions, complex lifetime annotations, and advanced unsafe Rust** ([rustify.rs, 2026](https://rustify.rs/articles/learning-rust-with-ai-tools-2026)) — exactly the category of error that burns hours in a hard-deadline build, because it's not "the code doesn't work," it's "the code doesn't compile and the fix is a lifetime-annotation puzzle."
- Countervailing anecdote worth weighing honestly: at least one practitioner reports Rust-with-AI as net faster than TypeScript-with-AI specifically because compiler errors catch classes of bugs at compile time that would otherwise surface as runtime debugging sessions later. This is a real, plausible dynamic for logic-heavy code — but ComplyLine's backend is closer to "plumbing between three HTTP APIs and a database" than logic-heavy state machinery, which is exactly the shape where that advantage matters least and the borrow-checker tax matters most (you spend Rust's safety budget on request/response wiring, not on business logic where bugs would actually be expensive).

No comparable friction shows up for Go. Go's design goal was always "boring, simple, fast to write," and nothing in the research or in general knowledge of the language indicates AI agents struggle with idiomatic Go the way they visibly do with Rust's ownership model — Go has no borrow checker, no lifetimes, and a small enough idiom set that Google is now shipping first-party AI tooling for it (Genkit Go, per the same 2026 field guide), a signal Go is being actively invested in for AI-adjacent backend work, not just tolerated.

## 4. Rust vs Go vs Python for this specific app shape

For an app whose real job is REST calls out, JSON in, rows into Postgres, JSON back to React — the performance and memory numbers that show up in every Rust-vs-X benchmark (Axum handling "~500K req/s per core," "30x more than Python (FastAPI)" per one 2026 head-to-head — [Medium, Kannan 2026](https://medium.com/@rameshkannanyt0078/fastapi-vs-actix-web-vs-axum-i-built-the-same-api-in-python-and-rust-the-results-broke-my-heart-2af5b40109a2)) are **not relevant to ComplyLine's actual bottleneck.** A hackathon demo serving a handful of concurrent users, where every request already blocks on a round-trip to AssemblyAI's own API, is never going to be throughput-bound by the backend language. This is the single clearest fact in this research: Rust's headline advantage (raw throughput, zero-GC latency) is real and well-documented, but it is not a variable that applies to this project's actual constraint, which is calendar days, not requests per second.

Where each language actually differs for this shape of work:

- **Python (FastAPI)** — fastest to write, easiest for an AI agent (best-trained language for code generation, bar none), official AssemblyAI SDK with 100K+ monthly downloads, SQLAlchemy is the most mature ORM of the three ecosystems by a wide margin, FastAPI's type-driven request/response models map directly onto "call three APIs, validate the shapes, write to Postgres, serve JSON." This is the zero-novelty, lowest-risk, fastest-iteration option — exactly why it's the one captain wants to avoid for novelty's sake, not because it's technically weak.
- **Go (Gin or net/http + sqlx/GORM)** — ~~official AssemblyAI SDK exists~~ **[CORRECTED: this SDK was discontinued in April 2025, see top of document — Go has no SDK advantage here.]** No borrow checker, no lifetimes — nothing in the research suggests AI agents fight Go's idioms the way they fight Rust's; Go's own design goal (small language, few idioms, explicit error handling instead of exceptions) is close to ideal for a coding agent generating a lot of similar-shaped HTTP-handler boilerplate. GORM and sqlx are both called "mature and stable" as of 2026 ([reintech.io Go DB comparison](https://reintech.io/blog/sqlc-vs-gorm-vs-sqlx-go-database-libraries-compared-2026)), and GORM's auto-migration and higher-level query builder is a genuine hackathon-velocity win over hand-writing SQL. Go is a real "new language" for anyone coming from Python/TypeScript — different enough to count as "out of comfort zone" — while carrying almost none of Rust's AI-tooling friction.
- **Rust (Axum + sqlx)** — no official AssemblyAI SDK (write your own typed request/response structs against `reqwest`), the ecosystem's own community assessment is that SQLx "just works" for async Postgres but Diesel-style compile errors can be "40 lines of generic type vomit" when something's wrong ([rustfinity.com 2026 ORM guide](https://www.rustfinity.com/blog/rust-orms)) — a real cost multiplier on debugging time specifically for an AI-driven build, where every failed compile is a round-trip the agent has to interpret and retry. Rust's safety guarantees (no null pointers, no data races, no use-after-free) are real engineering value — but they pay off hardest in long-lived, concurrency-heavy, or memory-sensitive systems. ComplyLine is a short-lived hackathon CRUD-plus-API-orchestration app with no concurrency-heavy state and no performance ceiling to hit. The insurance Rust sells is largely insurance this project doesn't need to buy.

## 5. "Out of comfort zone" as a goal vs. the stack becoming the bottleneck

This tension is real and worth stating plainly rather than smoothing over. Wanting to learn something new during a hackathon is a legitimate, non-technical goal — but it competes directly with the 30-day/AI-coding-agent constraint this repo's other research has already established as the real bottleneck for every idea on the list (see the "30-Day Completion" axis throughout `docs/hackathon-ideas.md`: repeatedly, the finding is that AI coding speed collapses code-volume risk but does **not** collapse "a real tuning/validation loop, an open design/research question" risk).

Rust's risk here is specifically that kind of loop: not "will the agent eventually produce working code" (it will), but "how many of the 30 days get spent on borrow-checker/lifetime debugging cycles that have nothing to do with ComplyLine's actual product logic." The research confirms this is a documented, current, named friction point (unreliable on "complex lifetime annotations," "40 lines of generic type vomit" on ORM errors) — not a stereotype. Go's claimed gentler learning curve holds up under this specific project's lens: nothing in the research shows Go creating an analogous category of AI-agent-specific friction, its official AssemblyAI SDK removes one integration-risk axis Rust doesn't have, and its ecosystem tooling (GORM, Gin) is rated equally mature to Rust's for this exact use case. Go gives captain a genuinely new language and idiom set (explicit error handling, goroutines/channels, no exceptions, no classes) without importing the one risk category — compiler-fight time — that is most likely to eat into a hard 30-day deadline.

## 6. Direct recommendation

**Go.** Not Rust, not Python.

- **Not Python** because captain explicitly asked for something outside his comfort zone, and Python is the safest, least-novel choice technically available here — correct default, wrong answer to the actual question being asked this round.
- **Not Rust** because the evidence, taken honestly rather than steel-manned toward the requester's stated interest, shows a real and current AI-coding-agent friction tax specific to Rust (lifetime annotations, ORM error legibility, no official AssemblyAI SDK to lean on) that has no work to pay for in this project — ComplyLine has no performance ceiling, no memory-safety-critical surface, and no concurrency complexity that would make Rust's guarantees worth their cost. This is precisely the situation this repo's other research flags as the dangerous pattern: a stack choice that risks becoming "an open design/research question" or tuning loop instead of the product being the thing that eats calendar days.
- **Go** delivers the "genuinely new language, real learning" goal captain wants ~~, has an official AssemblyAI SDK (a real, concrete integration-risk reduction Rust doesn't get)~~ **[CORRECTED: no such SDK edge — see top of document; both Go and Rust lack a maintained AssemblyAI SDK]**, has mature, well-regarded Postgres tooling (GORM/sqlx-equivalent) rated on par with Rust's own, and — per the available evidence — does not carry Rust's documented AI-agent-specific compile-time-fight tax. It's the only one of the three options that is simultaneously novel enough to satisfy the stated non-technical goal and low-risk enough not to threaten the same 30-day constraint every other piece of research in this repo treats as the real gating factor.
