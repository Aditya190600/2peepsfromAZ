## What this is

Submission repo for the **AssemblyAI Voice Agent Hackathon** (lablab.ai, Sep 1-30 2026, online, month-long, $10k prize pool). Two-person team: repo owner (Aditya190600) + collaborator (sujeevraja). ## Hard constraints (do not violate)

- **AssemblyAI-only voice infrastructure for the hackathon path.** Every default-configuration request (Get started, Try with no BYO key set) must go through AssemblyAI's Streaming API / Voice Agent APIs, with zero extra keys required - that's what breaks hackathon eligibility if violated. `server/providers/` (see below) is the one sanctioned exception: an *operator opt-in, BYO-key* registry that lets a non-default transcriber/model/voice be selected explicitly. It never changes what a fresh clone does by default and is out of scope for the hackathon video/eligibility - see `.claude/prds/provider-swaps.md`.
- **Deadline: Sep 30, 2026.** This is a fixed submission date, not a soft target.
- **Team size: 2.** Scope decisions accordingly - favor a demoable, judged-well project over an ambitious multi-service build neither person can maintain solo.
- **Submission needs a live deployed demo.** Host is Railway (long-running Node) with optional Railway Postgres persistence (the `postgres` addon declared in `.railway/railway.ts`, wired via the auto-injected `DATABASE_URL`) for the server `reportCache` Map. Do not use Vercel serverless for that Map. History stays in `localStorage`.

## Current state

Product (R3-21, selected idea - see `docs/hackathon-ideas.md`): a **post-hoc session compliance report**. It ingests one completed AssemblyAI Voice Agent API session and flags: (1) whether a TCPA consent event was logged before the call, (2) whether the AI nature of the call was disclosed in the first few seconds (state disclosure laws, e.g. CA AB 2905), (3) a generic PII-pattern scan (SSN/credit-card/account-number shapes) via a pluggable pattern-set architecture (`server/checks/patternPacks.js`), with optional HIPAA, GLBA, FERPA, PCI DSS, GDPR, and FCRA identifier/disclosure packs shipped as real drop-in extensions. This is **not** a live conversational advisor - the report is the deliverable, not a spoken conversation. Stack: React+Vite frontend, Node/Express backend, no database (pattern packs and checks are plain code modules, not stored rules). Uses AssemblyAI's managed Voice Agent API (`wss://agents.assemblyai.com/v1/ws`) purely for session-ingestion plumbing (token mint, mic capture, transcript log). See `README.md` for architecture and run/test instructions.

An earlier build drifted into a live CCPA/CPRA Q&A voice advisor that was never the selected idea; that direction was reverted in favor of the above.

Enterprise-credibility pass (see `docs/judging-criteria-and-enterprise-gap-assessment.md` for the full rationale): findings are severity-ranked with a headline risk verdict per report and a regulatory citation per check (`client/src/compliance.js`), the HIPAA, GLBA, FERPA, PCI DSS, and GDPR pattern packs are exposed as a real multi-select (joined since by TCPA and call-recording-consent packs that wrap the existing always-on checks rather than duplicating detection - see `docs/compliance-roadmap.md`), and LLM Gateway calls (`server/checks/llmGateway.js`) retry with backoff on 429 and are cached per session hash server-side (`server/index.js`) since the account's rate limit is tight (~2 calls/30s). Report history persists to `localStorage` (`client/src/reportHistory.js`) with a `/history` screen. The server `reportCache` Map may also persist to Railway Postgres so a Railway restart does not re-warm 12 Gateway calls. That table is not a substitute for browser history and does not store live audio.

Post-hackathon product work, built ahead of schedule and awaiting review (PR #78, epic `.claude/epics/provider-swaps/`): a **Vapi-style provider registry** (`server/providers/`) gives transcriber, model, and voice each an independent, swappable slot behind one small registry (`server/providers/registry.js`), with BYO keys stored server-side only in a gitignored local file (`server/providers/.provider-store.json` - never the client, never env). Every slot defaults to the existing AssemblyAI path with no key required; `/v1/token`, `/v1/transcribe-upload`, and `/v1/analyze-session` all resolve through the registry now instead of calling AssemblyAI directly. Second-vendor adapters exist for transcriber (Deepgram) and model (any OpenAI-compatible endpoint) - Deepgram's is unverified against a live account (no key available when it was written) but its interface is locked by `transcriberDeepgram.test.js`. `client/src/ProviderSettings.jsx` (rendered on `/try`) is the operator-facing panel: three dropdowns plus a "key configured" indicator, never a key value. The selection is process-wide, so `server/providers/router.js` gates both `PUT`s behind sign-in plus the same `QUALEVAL_OPERATOR_EMAILS` allowlist as QualEval's operator routes, and the panel renders only when `GET /v1/providers/config` reports `canEdit`. The Northstar boot-warm cache (`server/warmCache.js`) always runs the default AssemblyAI model path regardless of the live selection, so it keeps sharing its cache with default-provider requests - see the `requestCacheKey` comment in `server/index.js`.

Per-visitor sign-in for the public demo (opt-in, no schema/migration cost): `server/index.js` gates `/v1/token`, `/v1/analyze-session`, and `/v1/transcribe-upload` behind Clerk's `@clerk/express` `requireAuth()` only when both `CLERK_SECRET_KEY` and `CLERK_PUBLISHABLE_KEY` are set; unset (the default), those routes and the `/try`/`/sessions`/`/session` screens behave exactly as before - one shared anonymous visitor, no accounts. Clerk stores all user/session state itself; nothing new is persisted in this app. `client/src/App.jsx`'s `RequireVisitor` wrapper is the client-side half of the same gate, no-op when `VITE_CLERK_PUBLISHABLE_KEY` is unset.

Webhook-native pivot (see `docs/webhook-pivot-idea.md`), now push-based per a 2026-09-20 captain-approved redesign: the earlier design had ComplyLine subscribe to AssemblyAI's own webhook and poll AssemblyAI's API for the transcript with a ComplyLine-owned AssemblyAI key - that only worked for sessions on ComplyLine's own AssemblyAI account, since AssemblyAI scopes session/artifact access per account, and it was AssemblyAI-only. The **ingest endpoint** (`server/webhooks/ingest.js`, `POST /v1/ingest/:apiKey` in `server/index.js`) replaces it: the customer's own backend (already running their voice agent, on any platform) POSTs the transcript directly, in the `{turns: [{role, text, tMs}]}` shape `analyzeSession` already consumes. Auth is purely the ComplyLine API key in the path (`verifyApiKey`) - no AssemblyAI SDK call, signature verification, or AssemblyAI credential of any kind. Verifies the key and validates the payload synchronously, acks `2xx` immediately, then dispatches the existing `analyzeSession` pipeline asynchronously, off the response path. `requestCacheKey` (shared with `/v1/analyze-session`) lives in `server/warmCache.js`, not duplicated per-route.

AssemblyAI-native webhook ingest (real phone calls, no customer integration): alongside the customer-push `/v1/ingest/:apiKey` above, `POST /v1/webhooks/assemblyai` (`server/webhooks/assemblyaiWebhook.js`) is a registered AssemblyAI webhook subscription (`call.connected`/`call.ended`/`call.failed`) - AssemblyAI itself POSTs here when a phone call on this account's Voice Agent API ends, no customer-side code involved. Auth is `X-AAI-Signature` (HMAC-SHA256 over the raw body, keyed by `AAI_WEBHOOK_SIGNING_SECRET`), not a ComplyLine API key, so it's mounted with its own `express.raw()` ahead of the app-wide `express.json()` in `server/index.js` - re-parsing JSON before verifying breaks the signature. On `call.ended` it fetches the one-hour-lived `transcript_url`, normalizes AssemblyAI's `timeline.json` (`user_transcript`/`agent_text` pairs) into `{turns: [{role, text, tMs}]}`, and reuses `processIngestedSession` from `ingest.js` for analysis dispatch - no separate pipeline. There's no per-key pack scope on this path, so it always runs every pattern pack. See `docs/assemblyai-webhook-ingest.md` for the two-path comparison and how to test with a real phone call.

Try-tab persona selector (design approved in full, see `.claude/prds` history for the design report): `client/src/personas.js` defines 6 selectable personas (neutral default + flight booking agent, healthcare receptionist, bank teller, faculty records member, school nurse), each with a CAN/CANNOT-scoped system prompt/greeting/AssemblyAI voice and a "seed a compliance violation" toggle that swaps in one intentional failure targeting a real check (`ai_disclosure`, `pii_scan`, or the new `scope_adherence`). `useVoiceAgent.js`'s `connect(persona, seedViolation, recordCall)` resolves the persona into the one-time `session.update` sent on `ws.onopen` (system_prompt/greeting/voice all lock after `session.ready`, so persona choice only needs to be fixed pre-connect). Picking a persona in `Dashboard.jsx` auto-selects (opt-out, not opt-in) its matching industry pattern pack(s) from `packIds` (e.g. school nurse selects both HIPAA and FERPA). `server/checks/scopeAdherenceCheck.js` is a new, real product check (not demo-only) judging via the LLM Gateway whether the agent stayed within `session.persona.scope`; it's `n/a` for any session without a persona. Recording is opt-in per call (`recordCall`, default unchecked - live-call audio stays unstored by default): `useVoiceAgent.js` mixes the mic and agent-reply audio into one shared `MediaStreamAudioDestinationNode` (a single audio track, since `MediaRecorder` only encodes a stream's first audio track and silently drops the rest) and records that with one `MediaRecorder`, exposing `recordedBlob`; the Try UI offers Download (local only) and "Analyze this recording" (reuses the existing `/v1/transcribe-upload` pipeline) as two separate actions on purpose. The Try-as-webhook-sandbox handoff is now wired: when a non-neutral persona's call ends, `Dashboard.jsx`'s `runWebhookSandbox` POSTs the persona call's transcript (`lastSession`, via `analyzeClient.js`'s `ingestSession`) to `POST /v1/ingest/:apiKey` using an operator-pasted ComplyLine API key, instead of the direct `/v1/analyze-session` path - the same webhook receiver a real customer integration posts to. Ingest acks immediately and analyzes asynchronously server-side, so this action shows a sent/error status, not an inline report. See `docs/persona-selector-manual-test-matrix.md` for the live-call cases `node --test` can't cover.

Dedicated Examples page (relocated from Try's tabs, PR #125's original content, not new): playable samples and scripted violation demos live at `/examples` (`client/src/Examples.jsx`), reached from nav, so a fresh visitor can see a full compliance report with zero setup before touching the live-call Try flow. This route is deliberately not wrapped in `RequireVisitor` (`App.jsx`), and `server/index.js`'s `requireVisitorUnlessCannedSample` middleware (used only by `/v1/analyze-session`) bypasses the Clerk gate solely when the posted `session.sessionId` matches a known `SAMPLE_SESSIONS`/`NORTHSTAR_SESSIONS` fixture, substituting the server's own canonical copy of that session rather than trusting the request body - so a signed-out request can't smuggle arbitrary content past auth via a spoofed sessionId. Each playable sample is just call details, a waveform `AudioPlayer`, and an Analyze button, with one "Analyze fleet" button below the list (no separate fleet tab); the speaker-split/diarization demo and its unauthenticated `/v1/examples/diarize/:key` route were removed. Recording playback storage (the Railway bucket held open above is now provisioned and wired): a bucket named `storage` is linked to the `2peepsfromAZ` service via `${{storage.VAR}}` variable references - `RECORDINGS_BUCKET`, `RECORDINGS_BUCKET_ENDPOINT`, `RECORDINGS_BUCKET_REGION`, `RECORDINGS_BUCKET_ACCESS_KEY_ID`, `RECORDINGS_BUCKET_SECRET_ACCESS_KEY` (see `railway variable list --service 2peepsfromAZ` for the live set; never dump values). `server/recordingsStore.js` wraps `@aws-sdk/client-s3` behind `recordingsConfigured()`, same injectable-client pattern as `server/db.js`; when unset (local dev, no bucket linked) every caller degrades to client-only blob playback with a console log, not a crash. All recording routes live in `recordingsStore.js`'s `recordingsRouter`. `POST /v1/recordings/:sessionId` (raw body, audio content types only, `requireVisitor`-gated) uploads a recorded call to `live-calls/<visitorId>/<sessionId>.webm` - the owner is part of the key, so only the uploader can play (`GET /v1/recordings/:sessionId`, Range-aware for seeking, proxied so S3 credentials never reach the browser) or overwrite it, and anyone else gets a 404. `POST /v1/recordings/:sessionId/share` (owner only) mints a random 256-bit token (only its SHA-256 is stored, under `recording-shares/`) for a play-only `GET /v1/shared-recordings/:token` link - SessionInspector's "Share with audio" button. The plain `/sessions/:id` Share link never carries audio. `Dashboard.jsx` fires the upload as soon as `recordedBlob` is set, keyed to `lastSession.sessionId` via a ref (`recordingUploadRef`) so `runLiveReport` can await it and prefer the durable bucket URL over the local `blob:` URL once it resolves; that URL is what's saved onto the history entry as `recordingUrl` (`reportHistory.js`/`SessionInspector.jsx`'s `audioResolve.js` - a durable URL beats a sample's `audioKey`, which beats the in-tab-only `liveAudioBlobs.js` registry). Live report and history-reopened report both reuse `AudioPlayer.jsx` and the `Timestamp`/`Finding` click-to-seek wiring already built for the sample-upload path - no separate player was written. `AudioPlayer.jsx` also renders a client-decoded waveform (`decodeAudioData` on the same `src`, no new backend endpoint) with an optional `markers` prop (`{tMs, kind, label}`, `kind: "flag"` for a flagged finding) so a caller can overlay clickable timestamp markers directly on the waveform instead of only a list; `offsetMs` shifts marker/click positions the same way `seekAudio` already does for live-call recording offsets. `client/src/seek.js`'s `seekAudio(audioRef, tMs, offsetMs)` is the one seek implementation both `Dashboard.jsx` and `SessionInspector.jsx` call; a live recording starts only once the mic is live, so the session's `recordingOffsetMs` must travel with `recordingUrl` onto every history-entry write or seeks land late.

A completed live call is written to `reportHistory.js` the moment it ends, before any network call: `Dashboard.jsx`'s `useEffect` on `lastSession` saves a pending, transcript-only entry (`pending: true`), then auto-runs `runLiveReport()`, which fills in that same entry by id. `useVoiceAgent.js` sets `lastSession` on socket close too, not only on `session.ended`. A pending entry reopened in `SessionInspector.jsx` offers "Generate report"; "Regenerate report for last call" on `/try` updates the existing entry in place. See `docs/live-call-history-manual-test-matrix.md`.

The first landed half is a real, per-account **API key system** (`server/apiKeys.js`, migration `server/migrations/002_api_keys.sql`), which the separate webhook-receiver task depends on. Keys are per-Clerk-user, multiple per account, scoped to a set of compliance pack ids (or the `"all"` sentinel) from `server/packs/index.js`'s `PACK_IDS`, and carry a user-editable expiry (default `DEFAULT_EXPIRY_DAYS = 90`). Only a SHA-256 hash of the raw key is ever persisted; the raw value is returned once, at creation, and never again. This table requires Postgres (`dbConfigured()`, `DATABASE_URL`) - unlike `report_cache`, there's no in-memory fallback, since losing an account's keys on restart isn't acceptable for real customer credentials; `/v1/api-keys*` routes 503 when Postgres isn't configured. Unlike every other route in `server/index.js`, `/v1/api-keys*` also 503s when Clerk isn't configured (`requireRealAccount` middleware) - the anonymous single-shared-visitor fallback used everywhere else in this app is not acceptable for real API key pooling, so this is the one place that fallback is deliberately refused rather than degraded-but-working. `verifyApiKey(rawKey)` is the stable interface a future webhook receiver calls to authenticate an inbound request - see its doc comment in `server/apiKeys.js` before changing its return shape. The management UI lives at `client/src/ApiKeys.jsx` (`/api-keys`, in `PRODUCT_NAV`) - a GitHub-token-style flow (name, scopes, expiry, one-time raw-key reveal, list with edit-expiry and revoke). No component test runner covers it; see `docs/api-keys-manual-test-matrix.md`.

Storage backend: **Railway Postgres, not Supabase** (swapped 2026-09-21 - see `git log` on `server/db.js`/`server/reportCache.js`/`server/apiKeys.js` for the migration). `server/db.js` wraps a single `pg.Pool` keyed off the standard Railway-injected `DATABASE_URL` env var (`dbConfigured()`/`getPool()`); every query function takes the pool as an injectable last argument, same pattern the old code used for `fetchImpl`, so tests fake the pool instead of hitting a real database (`server/apiKeys.test.js`, `server/checks/reportCache.test.js`). `server/migrate.js` replays every `server/migrations/*.sql` file (idempotent `create table/index if not exists`) on every boot when `DATABASE_URL` is set - no separate migration step or tracking table. `report_cache` keeps its optional-with-in-memory-fallback behavior; `api_keys` keeps its hard-fail-without-Postgres behavior - both unchanged from the Supabase-era contract, only the backend moved.

**Live-call audio is stored only when the Try page's "Record this call" checkbox is on** (then it goes to the recordings bucket above). Otherwise `client/src/useVoiceAgent.js` streams mic PCM to AssemblyAI and plays reply PCM back through the Web Audio API in real time; neither is written to disk, blob storage, or a DB - only the text transcript (with per-turn `tMs`) is kept, in React state, lost on reload. `recordingConsentCheck.js`/`consentCheck.js` verify that recording/consent language was *declared* (spoken, or a `consentEvent` flag), not that audio was actually captured. Besides recorded live calls, the demo-upload path (`POST /v1/transcribe-upload`, via AssemblyAI's pre-recorded STT - a different product from the Voice Agent API) has real audio available for playback, since the client keeps the uploaded `File` as a local blob URL; every finding (from every check except `consent`, which has no audio position) carries a `tMs` so the UI can seek that player to it.

`client/src/SessionInspector.jsx` (mounted at `/sessions/:sessionId`) reopens one stored `reportHistory.js` entry with zero re-analysis (except a `pending` live-call entry, whose "Generate report" fills it in): Call tab (transcript + player when audio is available) and Evaluation tab (existing `Report` from `Dashboard.jsx`, reused rather than duplicated). Audio resolution order (`client/src/audioResolve.js`): `entry.recordingUrl` (durable, owner-scoped bucket URL) → `entry.audioKey` → `SAMPLE_AUDIO_URLS` (survives reload), else `client/src/liveAudioBlobs.js`'s in-tab-only registry of upload blob URLs by `sessionId` (dies on reload, since blob URLs never persist to `localStorage`). `entry.source === "live"` is the only history-entry field that exists purely to drive UI copy ("audio is stored only when recording is opted in") - it is not otherwise load-bearing.

Live-analysis metrics (Try-page feedback item 8): `server/checks/llmGateway.js`'s `callLlmGatewayWithUsage` (the default `complete` for the AssemblyAI model slot, `server/providers/modelGateway.js`) resolves `{content, usage: {inputTokens, outputTokens, totalTokens}, costUsd, model, durationMs}` from the Gateway's real `usage.input_tokens`/`output_tokens`/`total_tokens` fields (not OpenAI's `prompt_tokens`/`completion_tokens` - verified live per the standing convention above) and logs each call's tokens/cost/duration; `estimateCostUsd` prices it from a published-per-1M-token table (only `qwen3.5-4b-32k-fast` today) and returns `null`, not `$0`, for an unpriced model. The plain-string `callLlmGateway` (used by provider adapters, evals, and existing tests) is unchanged - `disclosureCheck.js`/`piiScan.js`/`scopeAdherenceCheck.js` accept either shape from their injected `llmGateway` option so a BYO OpenAI-compatible provider still works, just without usage/cost. `analyzeSession` (`server/checks/analyze.js`) sums every finding's `llmUsage`/`llmCostUsd` into the report's `usage` total and counts `status === "flag"` findings into `violationCount`, and fires an optional `onCheckComplete(finding, checksDone, checksTotal)` as each of its six checks resolves. `POST /v1/analyze-session` streams those as newline-delimited JSON when the request body sets `stream: true` (`client/src/analyzeClient.js`'s `analyze(session, packIds, onProgress)`); every other caller keeps the original single-JSON-response contract. `Dashboard.jsx`'s single-session live report and fleet report paths pass `onProgress` and accumulate it into `analysisProgress`/`fleetProgress`, which `compliance.js`'s `formatAnalyzingMessage` turns into the "Analyzing…" copy - real changing tokens-used/cost-estimate/violation-count numbers instead of a static message.

A fourth regulatory pattern pack, `server/packs/coppa.js` (COPPA, 15 U.S.C. §§6501-6506 / FTC Rule 16 CFR Part 312), joins HIPAA/GLBA/FERPA in `server/packs/index.js`'s `PACKS` map - registering a new pack there is the whole integration point; `piiScan`/`analyzeSession` pick it up automatically via `patternPackIds`. Unlike the identifier packs, COPPA's signals (self-stated age/grade under 13, a child disclosing their own name together with their school) are about *who the caller might be*, not a labeled data shape, so its regexes are looser judgment calls rather than structured-ID matches - treat `coppa` findings as lower-confidence signals, same caveat the pack's own `asserts` text states. The school nurse persona (`client/src/personas.js`) includes `coppa` in its `packIds` since it can end up talking to a student directly, not just a verified parent.

State-specific AI-disclosure/deceptive-practice packs (`server/packs/caSb1001.js`, `server/packs/caAb489.js`, registered in `server/packs/index.js`): CA SB 1001 (bot disclosure, whole-call scan, no fixed window) and CA AB 489 (self-claimed healthcare-credential detection - `physician`/`nurse`/credential-letter self-claims). Verified against enrolled bill text on 2026-09-24; **Texas SB 140 does not contain any AI/synthetic-voice disclosure or opt-out requirement** despite several AI-vendor marketing blogs (bloomreach, salesai, retellai) claiming a "30-second disclosure" rule - its actual text only expands telemarketing registration/bonding/consent to text messages (`capitol.texas.gov/tlodocs/89R/billtext/html/SB00140F.htm`). Don't rebuild a TX SB 140 disclosure pack from a secondary source without re-reading the enrolled text; see `docs/compliance-roadmap.md` for the note. This also extended the pack architecture: a pack can carry `check: (session, opts) => finding` instead of (or in addition to) `patterns`, for a requirement whose polarity or scope doesn't fit `piiScan.js`'s per-turn presence-is-bad model (e.g. SB 1001's absence-is-bad, whole-call scan). `analyzeSession` (`server/checks/analyze.js`) runs `pack.check` for any pack present in the caller's `patternPackIds`, same opt-in path as the PII packs - see `caSb1001.js`'s header comment for the reasoning.

## Standing convention: verify AssemblyAI docs before writing integration code

**Before writing or modifying any AssemblyAI integration code**, fetch `https://www.assemblyai.com/docs/llms-full.txt` live (it's ~95k lines; grep it, don't try to read it whole) and check the relevant `/docs/voice-agents/...` pages as needed. Do not rely on memorized/training-data parameter names or event shapes - this API has changed since most models' training cutoffs, and the docs disagree with common LLM assumptions in specific, easy-to-miss ways (verified live 2026-09-03):

- The session-config field for domain vocabulary is `session.input.keyterms` (a plain array), **not** `keyterms_prompt` - that name is used by the separate Streaming STT product, not the Voice Agent API.
- To cleanly end a Voice Agent session, send `{"type": "session.end"}` and wait for `session.ended`, **not** `{"type": "Terminate"}` - `Terminate` is the Streaming STT product's close message. Closing the socket without `session.end` leaves the session resumable (and billable) for 30 seconds.
- Tool definitions in `session.tools` use AssemblyAI's own flat schema (`{type: "function", name, description, parameters}`), not OpenAI's nested `{type: "function", function: {...}}` form.
- `reply.audio` carries its payload in the `data` field; `input.audio` carries it in the `audio` field - easy to conflate.
- The `GET /v1/voices` endpoint mentioned in prose docs is not a working REST endpoint in practice (returns a 426 WebSocket-upgrade response) - trust the documented voice catalog instead (e.g. `anna` is the spec-documented default).
- The LLM Gateway (`server/checks/llmGateway.js`) available-models docs page doesn't say which models a given account can actually call - Bedrock/Vertex/OpenAI-provider models (Claude, Gemini, GPT, etc.) 400 with `"Your account does not have access to this LLM Gateway model"` unless that provider is enabled on the account, verified live 2026-09-04. `qwen3.5-4b-32k-fast` is served directly by AssemblyAI with no provider gating and worked on this account; don't assume any specific model string is callable without a live test call against the real key.

When something you need isn't obviously in the docs dump, don't guess - grep harder or ask.

## Debugging the live voice call end to end

When a live-call bug report can't be pinned down from code reading alone, don't guess at an acoustic/hardware cause and patch blind - instrument the real pipeline and get evidence: proxy `window.WebSocket` (log every non-audio-frame send/recv type + timestamp) and hook `navigator.mediaDevices.getUserMedia` (to inspect the real `MediaStreamTrack` state, or to substitute a `MediaStreamAudioDestinationNode` fed by `decodeAudioData` on a real speech sample so genuine signal flows through the actual unmodified worklet/PCM16/WS code path when physical mic capture isn't available in the environment). Before trusting a "mic captured nothing" result, verify at the OS level independent of the browser (e.g. `sox`/`rec`, `osascript -e 'get volume settings'` for muted/zeroed input or output) - a sandboxed/CI machine's system input gain can be 0 by default, which looks identical to a code bug from inside the browser alone.

`useVoiceAgent.js` surfaces a `micSilent` flag (peak-amplitude check on captured PCM chunks, ~15s no-signal threshold) and `Dashboard.jsx` renders a banner when it fires - added because a genuinely dead input device previously failed completely silently, indistinguishable from a hung app.

## Product pivot: QualEval (2026-09-24, captain-approved, supersedes ComplyLine)

Active product direction is **QualEval**, a black-box qualitative acceptance-testing platform for AI voice agents (treat any target agent as reachable only by phone number; generate scenarios/personas via the LLM Gateway, run real calls, judge the transcript pass/fail with evidence) - not the ComplyLine compliance-report framing above, which is superseded and should not be built on further unless told otherwise. See `docs/qualeval-foundation.md` for the full architecture and what this foundation slice built vs stubbed. New route `/qualeval` (`client/src/QualEval.jsx`), new backend module `server/qualeval/` mounted at `/v1/qualeval`, new tables `qualeval_evaluations`/`qualeval_scenarios`/`qualeval_runs` (`server/migrations/003_qualeval.sql`, same hard-fail-without-Postgres contract as `api_keys`).

**Real outbound call-placement bridge (Twilio -> AssemblyAI Voice Agent).** `POST /scenarios/:id/runs` now places a real outbound PSTN call when `TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN`/`QUALEVAL_PERSONA_NUMBER` are configured (all three set on the deployed `2peepsfromAZ` Railway service; read via `process.env`, same pattern as `ASSEMBLYAI_API_KEY` - never print their values in logs/status/PR text). Without them the run stays the original honest `pending` stub. Architecture, verified live against both vendors' docs 2026-09-24:

- AssemblyAI's own documented Twilio integration (`/docs/voice-agents/voice-agent-api/connect-to-twilio`) is **inbound-only SIP trunking** (Twilio routes calls to `sip:sip.assemblyai.com`, no media server) - it does not cover QualEval's need (an outbound call where *we* are the caller). The real mechanism here is Twilio Media Streams: a bidirectional `<Connect><Stream>` TwiML verb (`server/qualeval/twilioVoice.js`, `POST /v1/qualeval/twilio-voice/:runId`, Twilio-signature-verified) that bridges the call's raw audio over a second WebSocket (`server/qualeval/twilioStream.js`, `wss://.../v1/qualeval/twilio-stream`, attached to the raw `http.Server` via `attachTwilioStreamServer` since Express has no WS support) to a server-side AssemblyAI Voice Agent session (`server/qualeval/bridgeSession.js`).
- Both legs use `audio/pcmu` (G.711 mu-law, 8 kHz) - Twilio's native Media Streams codec and one of AssemblyAI's documented `input.format`/`output.format` encodings - so every media payload is relayed byte-for-byte with zero resampling.
- Role naming is intentionally swapped in `bridgeSession.js`: AssemblyAI's `transcript.user` (what we fed it - the phone audio) becomes QualEval turn role `"agent"` (the target under test), and `transcript.agent` (AssemblyAI's own LLM, playing our simulated caller) becomes role `"user"` - see that file's header comment before changing it.
- `server/qualeval/callBridge.js`'s `placeCall` never hardcodes a phone number; `from` is always `QUALEVAL_PERSONA_NUMBER`, `to` is always the evaluation's `agentPhoneNumber`. Run state machine (migration `004_qualeval_call_states.sql` widens `qualeval_runs.verdict`): `pending` (not yet run/no Twilio) -> `in_progress` (call placed) -> `awaiting_evaluation` (transcript landed, evaluator not yet run) -> `pass`/`fail` (evaluator completed) or `error` (call placement or the bridge itself failed - distinct from an evaluator `fail`, and never fabricated).
- Twilio number purchase, the two-number-pool rotation, and the real inbound call handling direction (target-agent-calls-QualEval) remain out of scope/unbuilt. `QUALEVAL_AGENT_NUMBER` (the second Railway-configured number) is reserved for that future inbound direction, but today also answers as a real, bridged AssemblyAI target agent for MVP/demo verification of the outbound bridge - see the next bullet. `server/qualeval/demoAgentProvision.js` self-provisions its Twilio Voice Configuration on every boot (required before Twilio treats any inbound leg to it as answered, including the leg the outbound bridge itself creates - a number left unconfigured fails at `duration: 0` with no Twilio-side error to debug), pointed at `server/qualeval/demoAgentVoice.js`'s `POST /v1/qualeval/demo-agent-voice` route - see `docs/qualeval-demo-agent-number.md`.
- **Real demo target agent answering `QUALEVAL_AGENT_NUMBER`** (`docs/qualeval-demo-target-agent.md`): `demoAgentVoice.js` returns the same `<Connect><Stream>` pattern as the outbound side, bridged (`server/qualeval/targetAgentStream.js` -> `bridgeSession.js`) to a real AssemblyAI Voice Agent session instead of a static scripted line. Each variant is an AssemblyAI **stored agent** (`POST`/`PUT /v1/agents` - `server/qualeval/demoAgentAgents.js`), bound by `agent_id` (mutually exclusive with inline `system_prompt`/`greeting`/`voice`/`input`/`output` on a session.update - `bridgeSession.js`'s `agentId` param), not prompt text stored in this repo's own DB. `server/qualeval/demoAgentDefaults.js`'s `DEMO_AGENTS` catalog is the single source of truth for which agent keys exist - a compliant/flawed pair per domain (banking `compliant`/`flawed`, `healthcare-*`, `flight-*`; bodies have `input`/`output.format` fixed to `audio/pcmu`, since that has to live on the stored agent once `agent_id` is used). `qualeval_demo_agent_variants` (migrations `005`/`008`) just maps each key to its `agent_id`; `demoAgentAgentsProvision.js` inserts a row for any new catalog key on boot and creates its agent only the first time the row has no `agent_id` yet. `qualeval_demo_agent_state` is a single-row runtime toggle for which agent is currently active, since there's only one number - but it is only the default: an evaluation's own `demo_agent_key` (migration `011`, picked on the QualEval create/edit forms) decides which agent answers that evaluation's scenario calls, handed from `placeCall` to the target leg through `callBridgeBroker.js` before dialing (see `docs/qualeval-demo-target-agent.md`'s "Which agent answers"). Don't make scenario calls read the global toggle again. The Settings page (`/settings`, `client/src/Settings.jsx`) switches it and shows both numbers, backed by `GET/PATCH /v1/qualeval/demo-agent/variants` (PATCH's `systemPrompt`/`greeting`/`voice` forward to `PUT /v1/agents/{agentId}`) and `POST /v1/qualeval/demo-agent/active` (`server/qualeval/demoAgentConfig.js`, `router.js`) - see `docs/qualeval-demo-target-agent.md`. Those routes, the Settings nav entry, and `/config`'s `personaPhoneNumber` are operator-only (`server/qualeval/operatorAccess.js`): `QUALEVAL_OPERATOR_EMAILS` (comma-separated, case-insensitive) is matched against the signed-in Clerk user's verified emails, non-operators get 403 (enforced per route handler by `router.js`'s `requireOperator`), unset fails closed, and only the exact value `*` opens it to everyone (a `*` inside an email list is ignored); `/config`'s `isOperator` drives the client-side hiding. Phone Evals access uses a separate, non-operator allowlist - see the "Phone Evals access is two-tier" paragraph below. `bridgeSession.js`'s `transcriptUserRole`/`transcriptAgentRole` options make its role-swap logic configurable because this side needs the OPPOSITE mapping from the caller side - re-read that file's header comment before touching either direction's role mapping.

**The persona leg and the target-agent leg hear each other over the real phone line** - each leg's `<Connect><Stream>` sends its own AssemblyAI session's speech out on that leg and Twilio carries it to the other leg's Media Stream as inbound `media`, same as for a real external caller. There is no server-side audio relay: an earlier `callBridgeBroker.js` cross-feed (added 2026-09-25 on the mistaken belief that Twilio did not carry audio between the legs - an artifact of the target side's dropped-`reply.audio`/lost-`start` bugs below) made each AssemblyAI session hear the other party twice, once early and once in real time, and the two agents talked over each other from the first seconds of every call (reproduced live 2026-09-27 with Twilio dual-channel recordings). Don't reintroduce a server-side audio hand-off between legs. `callBridgeBroker.js` now only links the target-agent leg to the run that placed the call (for `qualevalRunId` on its production-call record, and the evaluation's `demoAgentKey` so the right agent answers) via `registerPlacedRun`/`claimPendingRun` (placement registers only runs dialing a number our demo-agent-voice route answers, so an outside-number run can never claim a real Phone Evals caller); only one QualEval call is expected in flight against the single demo number at a time. `bridgeSession.js` also sends Twilio a Media Streams `clear` when AssemblyAI reports an interrupted reply (`reply.done` `status: "interrupted"`), since Twilio otherwise keeps playing the cancelled reply's already-buffered audio over the barge-in.
- **`<Stream url>` cannot carry the run id as a query string** - confirmed live 2026-09-24 (the real Twilio-originated WebSocket upgrade request's `req.url` had no query string at all) and in Twilio's own docs (`/docs/voice/twiml/stream#custom-parameters`: the `url` "does not support query string parameters"). A `?runId=` there is silently dropped, so every real outbound call's Media Stream was rejected the instant Twilio connected (duration-0 call, Twilio error 31921, no useful detail from Twilio's own notifications/alerts APIs). `twilioVoice.js` passes the run id as a `<Parameter name="runId">` instead; `twilioStream.js` reads it back from the `start` event's `start.customParameters.runId` (only knowable once Twilio actually connects), buffering any earlier messages until the run/scenario/token lookup resolves and `createBridgeSession` takes over. Don't reintroduce a query-string-based id for this route or any other Media Streams `<Stream url>`.

**The simulated caller hangs up itself once the conversation is over** (`bridgeSession.js`'s `END_CALL_TOOL`, enabled only on the persona leg via `endCallTool: true` in `twilioStream.js`; the run's end reason is `end_call`). Without it the two agents keep trading goodbyes, resetting the silence watchdog, until `DEFAULT_MAX_DURATION_MS`. Hangup waits for the goodbye to play out (Twilio `mark` echo), and an `interrupted` end_call reply still hangs up once the far end's farewell turn lands rather than cancelling - see the `tool.call`/`reply.done` handling and its comments in `bridgeSession.js` and `bridgeSession.test.js`. The silence watchdog, max-duration cap, and `DEFAULT_HANGUP_TIMEOUT_MS` stay as backstops.

**The simulated caller waits out the target's pauses between sentences** (`twilioStream.js`'s `CALLER_TURN_DETECTION`, sent as `session.input.turn_detection`) and is prompted to speak each reply without written hesitations (`callerPrompt.js`) - with AssemblyAI's adaptive defaults each side took the other's intra-turn pause as its turn, and one such collision kept the rest of the call talking over itself. The demo target agents need the same wait on their side (`demoAgentDefaults.js`'s `TARGET_TURN_DETECTION`, stored on each AssemblyAI agent's `input` and reconciled onto already-provisioned agents every boot by `demoAgentAgentsProvision.js`) - without it the target answered inside the caller's between-sentence pauses, worst at wind-down where closings are several short sentences. Measure turn-taking changes on real calls against Twilio dual-channel recordings, not from the transcript.

**A run is judged on its recording's transcript, not the live session's** (`server/qualeval/callTranscription.js`): after the call, `twilioStream.js` (and `targetAgentStream.js` for Phone Evals) transcribes the recorder's two legs as one stereo file with pre-recorded multichannel STT. The live Voice Agent session drops or mishears the far end wherever the two parties overlap and reports its own replies as spoken even when Twilio discarded them unplayed on a barge-in, which produced false "agent never asked" failures. Live turns remain the live-view feed and the fallback when there is no recording or transcription fails.

**A run can be stranded unfinished (`pending`/`in_progress`/`awaiting_evaluation`) with no in-process owner left to advance it** - placement dispatch, the call bridge, and the evaluator all live in the app process, so a Railway redeploy mid-call (routine) or a Media Streams WebSocket upgrade that never reaches `twilioStream.js` leaves the run stuck. `store.expireStaleRuns` (bounds in `STALE_RUN_AFTER_MS`, each longer than the real work it covers, e.g. `in_progress` > ring + `DEFAULT_MAX_DURATION_MS` + `CALL_TRANSCRIPTION_TIMEOUT_MS`) marks such runs `error` and is called at read time by `router.js`'s `reconcileStaleRuns` before every run-state read, so it survives the restarts it cleans up. This replaced an in-memory 5-minute `setTimeout` watchdog that died on every deploy and was shorter than the 5-minute call cap. The QualEval page also polls (`RUN_POLL_INTERVAL_MS` in `client/src/QualEval.jsx`) while any latest run is unfinished - there is no push channel, so without polling a page loaded mid-call shows "Call in progress…" forever.

**Inbound calls to `QUALEVAL_AGENT_NUMBER` can have a few seconds of silence right after Twilio answers**, before the Media Streams WebSocket reaches `targetAgentStream.js` and any AssemblyAI audio can play - observed at ~5-6s live 2026-09-26 against Railway (Twilio's own WS connect, before any of our code runs; zero Twilio errors logged). Do NOT cover it with a filler `<Say>` (e.g. "One moment please.") in `demoAgentVoice.js`: a calling voice agent - including every QualEval persona - hears the filler as the agent's opening turn and answers it, talking over the real greeting (reproduced live 2026-09-27; that filler was removed). If this gap matters again, re-verify with a real call and read Twilio's Events.json plus Railway logs, not assumptions.

**Outbound reply audio could be silently dropped on a real inbound call to `QUALEVAL_AGENT_NUMBER`** if AssemblyAI's `reply.audio` won the race against Twilio's own Media Streams `"start"` event - `bridgeSession.js`'s `reply.audio` handler only forwarded audio to the real Twilio leg once `streamSid` was known (set by `"start"`), and the two events arrive over independent sockets with no ordering guarantee. Confirmed live 2026-09-26 against a real inbound call (CallSid `CAc1f6b4cf4f0cd6b9c0699cd5006c3bbc`): Twilio Voice Insights showed clean `pcmu`/zero packet loss/zero jitter but `Silence Detected: true` and the caller hanging up, while our own server logs for the same call showed real `transcript.agent`/`transcript.user` turns - proving AssemblyAI generated speech and inbound audio worked, but the outbound bytes never reached Twilio's stream. Fixed by buffering `reply.audio` payloads that arrive before `streamSid` is known and flushing them once `"start"` sets it (`bridgeSession.js`'s `pendingReplyAudio`), mirroring the early-message buffering `twilioStream.js` already used for its own async lookups. Covered by a `bridgeSession.test.js` case that emits `reply.audio` before `"start"` and asserts it still reaches the Twilio leg once `streamSid` lands - re-check that test (not just a live call) if this handler changes. That fix alone did not restore audio: `targetAgentStream.js` also dropped Twilio's `connected`/`start` messages outright, since they arrive the instant the socket opens while the handler is still awaiting the variant lookup and token mint, before `createBridgeSession` attaches its listener - so `streamSid` was never set and `pendingReplyAudio` never flushed (production logs 2026-09-25: every inbound bridge log line stayed `[no-call-sid]` through hangup, `twilio event start` never logged). It now buffers every message from connection time and replays it once the session exists, same as `twilioStream.js`. Verify inbound audio with a real phone call and check for `twilio event start` plus a real CallSid in the bridge logs.

**Phone Evals is separate from Qualitative Evals** (captain-directed 2026-09-27): a call that dials `QUALEVAL_AGENT_NUMBER` directly (not a QualEval-placed scenario run) is never attributed to a QualEval evaluation - it used to be, via a dialed-number match against `qualeval_evaluations.agent_phone_number`, which dropped real callers into whichever evaluation set targeted that number. The moment such a call ends, `server/qualeval/postCallAnalysis.js` runs two analyses one after the other (not concurrently - both hit the LLM Gateway's tight rate limit): a ComplyLine compliance report (`server/qualeval/phoneCompliance.js` -> `analyzeSession`, with the industry pack matching the answering demo agent's domain - banking `finance`, healthcare `hipaa`; the caller dialing in counts as consent, same stance as the Try page's live call) stored on `production_calls.compliance_*`, then a pass/fail score against the answering agent's own live system prompt (`server/qualeval/phoneEvaluation.js`). The `/phone-evals` page (`client/src/PhoneEvals.jsx`, `GET /v1/qualeval/phone-evals`) is a mail-client layout - every call newest first on the left, the picked call's report on the right - that polls while a call or its analysis is unfinished; `POST /v1/qualeval/phone-evals/:callSid/analyze` re-runs both analyses (the way back from a rate-limited check). `production_calls` has no evaluation link. Which agent answers is Settings' operator-only Target agents switch (`qualeval_demo_agent_state`), not Settings' Call persona, which only pre-selects the Voice Compliance browser-call persona (`client/src/personaPreference.js`, localStorage). The Target agents section stays operator-gated: with `QUALEVAL_OPERATOR_EMAILS` unset nobody sees it.

**Phone Evals access is two-tier, not operator-only** (PRs #230/#233/#235/#238, superseding the operator-gated description above): a separate allowlist, `QUALEVAL_ADMIN_EMAILS` (`isPhoneEvalAdmin`, `server/index.js`), grants full access - every call, no setup required. Anyone else can self-serve access by importing their own inbound Twilio number (`client/src/PhoneEvalsSetup.jsx`'s `PhoneEvalsSetupSection`, rendered in `Settings.jsx` for non-admins, reusing the existing `POST /v1/telephony/imports/twilio` from the ComplyLine number-import feature, `server/telephony/store.js`); `server/qualeval/phoneEvalAccess.js`'s `canAccessPhoneEvals`/`canViewPhoneEvalCall` then scope both page access and per-call visibility to only calls whose `to_number` matches a number that visitor registered. The `/phone-evals` nav link and page gate on `canAccessPhoneEvals` (`Chrome.jsx`), not `isOperator` - a signed-in visitor with no Twilio number sees a setup prompt (`PhoneEvalsSetupGate`) instead of the page. A scenario run's inbound leg is excluded from Phone Evals by `qualeval_run_id` and by coming from `QUALEVAL_PERSONA_NUMBER` - don't reintroduce a phone-number-to-evaluation lookup.

**QualEval run call recordings** (captain-approved 2026-09-25, always-on - no opt-in checkbox, since the app itself places the call, not a live human caller): `server/qualeval/callRecorder.js`'s `createCallRecorder` buffers both call legs' raw PCMU frames (Twilio's `media` events and AssemblyAI's `reply.audio`, both already flowing through `bridgeSession.js` via its new `onIncomingAudio`/`onOutgoingAudio` callbacks) into one mixed mono PCM track, one buffer per leg written in place and summed only across legs. Frames are positioned on `bridgeSession.js`'s call timeline (`callClockMs`, also used for transcript turn `tMs`): incoming at Twilio's own `media.timestamp`, outgoing at Twilio's playout position (back to back, reset by a barge-in `clear`). Never position frames by their arrival time in this process - Twilio's frames arrive with heavy jitter, which makes the recording choppy (see `callRecorder.js`'s header comment and `callRecorder.test.js`). `twilioStream.js`'s `onFinished` encodes it to WAV and uploads via `server/recordingsStore.js`'s new generic `uploadObject`/`getObjectByKey` primitives (the same S3 client/bucket the Try page's live-call recordings use, just keyed `qualeval-calls/<runId>.wav` instead of owner-prefixed, since a run's ownership is already enforced by `store.getRun`'s `clerk_user_id` join rather than by the S3 key), then writes the serving route onto `qualeval_runs.audio_ref` via `store.attachAudioRef`. `GET /v1/qualeval/runs/:id/audio` (`router.js`) proxies it Range-aware, same shape as `/v1/recordings/:sessionId`. `client/src/QualEval.jsx`'s `RunResult` renders it with the same `AudioPlayer`/`Timestamp`/`seekAudio` primitives the Try page's `SessionInspector` uses for click-to-seek. Recording upload is best-effort (`recordingsConfigured()` false in local dev without a bucket linked - the run's transcript/verdict are unaffected either way). The target-agent leg (`targetAgentStream.js`) records the same way into `production-calls/<CallSid>.wav` for Phone Evals.

**QualEval live listen-in** (during a call, not after): the persona leg's bridge (`twilioStream.js`) already carries both sides - Twilio `media` is the target agent, AssemblyAI `reply.audio` is our simulated caller - so it also publishes each frame, each transcript turn (`bridgeSession.js`'s `onTurn`), and barge-in clears to `server/qualeval/liveCallHub.js`, an in-process read-only fan-out. `GET /v1/qualeval/runs/:id/live` streams that as Server-Sent Events (raw base64 `audio/pcmu` frames, no server-side resampling); `client/src/liveCallAudio.js` decodes mu-law and schedules it through Web Audio near the live edge, in an 8 kHz `AudioContext` with every frame on the sample grid (at the hardware rate each 20 ms frame's buffer is resampled on its own and clicks at its edges, which sounds scratchy) (it deliberately drops a stale backlog if a proxy releases the stream in bursts - a Cloudflare quick tunnel buffers SSE ~6 s, Railway's edge was not measured). Nothing published to the hub is ever fed back into a call leg - don't turn it into an audio path between legs (see the removed `callBridgeBroker.js` cross-feed above). Listening is on by default for every in-progress run via the page-wide "Auto-play live call audio" checkbox (per-viewer `localStorage`, default on when unset); a viewer opts out per scenario card ("Stop listening") or page-wide by unchecking it. A listener that opens while the call still rings waits for the bridge to start (`subscribe`'s `waitForStart`).

Compliance Examples folded into the Try page as a tab (2026-09-25): `client/src/Examples.jsx` now exports `ExamplesPanels({ navigate, topTabBar, onShowLiveCall })`, the reusable content (pattern packs + samples/scripted/fleet sub-tabs + report) with no `AppShell`/route wrapper of its own. `client/src/Dashboard.jsx` renders it as the "Compliance Examples" tab (`sessionTab === "examples"`) inside the "Voice Compliance" nav page (`/try`) alongside "Live call", swapping in `ExamplesPanels` for the whole `<main className="layout">` body of the Try page rather than nesting it inside the live-call panels. The standalone `/examples` route (`Examples`, `Examples.jsx`'s default export) is unchanged and still works exactly as before - including staying outside `RequireVisitor` (App.jsx) for zero-setup access - it just wraps the same `ExamplesPanels` in `AppShell`. `chromeNav.js`'s `/examples` nav-rail entry is hidden (not deleted), same pattern as other folded-in routes. Note `Dashboard.jsx` and `Examples.jsx` import from each other now (`ExamplesPanels` one way, `FleetView`/`Report`/`sampleLabel`/etc. the other) - safe only because neither file touches the other's imported bindings at module top level (only inside component bodies/JSX); don't reintroduce a top-level use of a cross-imported binding in either file without checking for the circular-import TDZ crash first.

## Dependency hygiene

`server/package-lock.json` and `client/package-lock.json` are committed - do not gitignore them. `server/package.json` pins `qs` via an `overrides` entry (body-parser hard-pins a vulnerable `qs` version transitively; the override is the fix, not a workaround to remove later). It also overrides `uuid` to `^11.1.1` for the same reason: `exceljs` (the QualEval scenario .xlsx export, `server/qualeval/scenarioExport.js`) pins a `uuid` with a moderate advisory; v11 still ships the CommonJS build exceljs `require`s. `client/package.json` is on Vite 7.x deliberately, not the audit-suggested Vite 8 - v8 ships the experimental rolldown-vite engine and `@vitejs/plugin-react` doesn't officially peer-support it yet. On a fresh macOS install `npm install` warns that `fsevents`'s install script isn't in `allowScripts`; that's expected and safe to leave unapproved (fsevents is an optional macOS-only file-watcher acceleration, not required for `vite`/`npm test`/`npm run build` to work).
